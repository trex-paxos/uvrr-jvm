# uvrr-core: the uVRR protocol core

## What this module is

The uVRR consensus protocol: viewstamped replication (VRR-2012) with eras, weighted quorums,
a boot-gate marker schedule, incarnation bumping (reincarnation), learner transfer, and the
fused-batch reconfiguration path. Sans-I/O throughout: the state machine consumes one `Input`
and returns a list of `Effect`, and every side effect is the caller's business.

Package `com.github.trex_paxos.core`. No dependency on `uvrr-lib`; the Paxos engine in
`uvrr-lib` is the outgoing implementation this module replaces, not a dependency of it.

## The source of truth is Rust, and it is not this repository

`github.com/lua-lunet/uvrr-core` is the reference implementation. It is normative for:

- the **wire codec** (`wire.rs`): the 20-byte header `(tag: u32, era: u32, view: u32, slot: u64)`,
  big-endian, no bit packing, for every tag. A byte that moves is a protocol change, not a port
  detail. This module's `wire` package reproduces it exactly: same tag discriminants
  (2-10, 13-17; 11 and 12 stay reserved), same wire names, same field widths.
- the **protocol semantics**, and the documents that state them:
  `docs/uvrr-protocols.md`, `docs/uvrr-fuse.md`, `docs/uvrr-durability-model.md`,
  `docs/uvrr-io-obligations.md`, `docs/architecture.md`.
- the **formal statements**: `formal/VrrCore*.tla` (TLA+, with its `.cfg` model files) and
  `formal/uvrr-lean/` (Lean). They live Rust-side and are cited, not forked.

When this module and the Rust crate disagree, the Rust crate wins and this module is the bug.
Disagreements are fixed here, never by editing the Rust reference to match.

## The compliance duty

Conformance is defined in the Rust repository at `docs/uvrr-host-compliance.md` §6. An
implementation conforms when it:

1. implements the **abstract host interface** over its own bindings, including the normative
   wire codec;
2. runs **every case** in the Rust repository's corpus
   (`tests/compliance/corpus/*.json`, one file per family) and passes every named expectation;
3. adds no behaviour the corpus forbids — an emission beyond the named multiset fails the case.

The corpus is the executable statement of the protocol's obligations. It is language-neutral
by construction: nothing in a case is expressed in Rust, so a Java, Zig or Lua harness runs the
same files over its own bindings. Each case pins:

- the setup script over the host interface (`provision`, `settle`, `propose`, `reconfigure`,
  `tick`, `tick_all`, `deliver`, `deliver_all`, `crash`, `restart`, `halt`, `boot`, `announce`,
  `gossip`);
- one input transition, either a hex-encoded datagram or a host event;
- the exact multiset of datagrams delivered afterwards — each named datagram exactly once, and
  nothing further. Silence is asserted by an empty list;
- the per-node post-state: `status`, `era`, `view`, the `accepted`/`committed`/`applied`
  frontiers, the `journal`, the `members` and `weights`, the `markers` schedule, and
  `witnesses`. Unnamed fields are unconstrained; named fields MUST match.

Two grammar rules bind the rendering, and both are load-bearing:

- the journal states payloads as abstract text — a host operation as its UTF-8 text, a typed
  cluster operation as its abstract name with `system:counter` arguments (`init order=1:1,2:1,3:1`,
  `increment 2:1`, `double`, `halve`, `join 4:1 at 3`, `leave 4:1`, `batch [...]`).
  **Rust debug formatting must never appear in journal content.**
- the marker schedule renders each round as `Marker@system:counter` with `Marker` one of
  `Stopping`, `Stopped`, `Restarting`, `Joining`, interleaved with the `drain` the halt schedule
  forces strictly between its rounds.

The corpus is authored by the Rust side and is regenerated by *its* exporter
(`cargo test --all-features --test compliance -- --ignored export_corpus`), whose output MUST
equal the committed files. This module therefore replays the corpus and never edits it.

| host binaries | maelstrom, timeout-policy, uvrr-reconfig | none |

What is already faithful: the message surface is complete — all 14 `Body` variants are declared
and handled, as are all 10 `Input` variants; the `wire` package matches the normative codec
tag-for-tag and field-for-field; `NodeId` packs as a single `u32`.

What is missing, in the order it must be done:

1. **the compliance harness.** The abstract host interface over `Replica`, plus the corpus
   reader and the post-state renderer. Until this exists, no case has ever run against this
   module and the 41 unit tests say nothing about conformance.
2. **the corpus replay.** 73 cases in 10 families, byte-exact deliveries. The first replay is
   the only thing that can locate the semantic gaps, and it is expected to find them: the Rust
   state machine splits into `normal`, `view_change`, `reincarnation`, `transfer`,
   `plan_execution` and a 3,245-line `mod`, where this module has a single 1,278-line `Replica`.
   Expect divergence in the view-change, transfer and reconfiguration paths, not in the
   data model.
3. **the exhaustive suites.** The Rust side proves identity law, the crash shape and the view
   machine with mint-based random lawful identities per run. Fixed corpus vectors are
   supplementary, never a substitute: the corpus pins vector identities as ordinary ones and
   forbids special-casing them.

## The zero-dependency property

The Rust crate guarantees (decisions W2, W3) that a consumer with `default-features = false`
pulls in zero transitive crates, so the core can be vendored into a build with a frozen or
audited dependency set. This module must keep the same property: the shipped jar has no runtime
dependencies.

Therefore anything the compliance harness needs to read the corpus's JSON — a parser, a
minimal reader — belongs in **test scope**. The Rust side makes the same cut: its compliance
runner is `#![cfg(feature = "serde")]`, so the corpus reader is opt-in and the default build
stays dependency-free.

The inherited `lombok` dependency is `provided` and is not used anywhere in this module's
sources; keep it that way, so the annotation processor never becomes a build-time dependency of
a consumer who only wants the core.
